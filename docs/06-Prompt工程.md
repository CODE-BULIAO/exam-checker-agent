## 一个检测 Prompt 分成哪些部分

文本类检测 Prompt（错别字、语义、标点……）有一套稳定的「解剖结构」：

```
# 角色            一两句把模型定位成「只检测、不思考、不解题」的扫描器
# 输入说明        reference（只读，禁止对它报错）；detection_content（要被检测的最终文本）
## 核心目标       精确说明检测什么、不检测什么
## 严格禁止       禁止解题/评价/扩大范围/对 reference 报错
## 工作流程       1) 前置判断（空内容？找错题？图片占位？）
                  2) 执行检测（具体错误模式 + 例子）
                  3) 审慎报告（置信度门槛，常为 ≥0.7）
## 样例           正反例对照
## 规则           严重度分级（严重 / 轻微 / 不报告的情况）
## 最终输出要求   error_type 字段「必须且只能」是本任务对应类型，越界一律不输出
+ 固定输出 JSON 结构（全任务共用模板）
```

设计要点：

- **角色压成「扫描器」**：明确「只检测不解题」，避免模型跑去做题、给学术评价、扩大检查范围。
- **reference 只读**：参考材料只帮助理解题意，**禁止对它报错**——否则会把背景资料里的内容也当题目报一堆假错。
- **置信度门槛**：把「拿不准的别报」写进 Prompt（≥0.7），这是压低误报率的第一道闸。
- **error_type 锁死**：每个任务的 Prompt 末尾强约束输出类型只能是自己那一类，杜绝类型漂移（见 [04](04-错误类别与分类.md)）。

## 固定输出 JSON 结构（全任务共用）

所有检测任务复用同一份输出模板，便于下游统一解析、聚合、入库：

```json
{
  "think": "完整推理链：[任务分析]→[执行回溯]→[最终决策]→[状态确认]（≤800字）",
  "reason": "一句话结论（≤60字）",
  "quality_score": 0.0,
  "overall_confidence": 0.0,
  "has_error": false,
  "total_errors": 0,
  "errors": [
    {
      "error_type": "本任务对应类型",
      "position": "人类可读的定位",
      "original_text": "出错原文（与原文完全一致，越精简越好）",
      "anchor_text": "用于召回定位的连续锚点（比 original_text 多些上下文，禁止含占位符，便于在 Word 中检索）",
      "correction": "修改后的内容",
      "description": "错在哪里（≤2句，禁推理过程）",
      "suggestion": "操作指令+正确文本（≤3句，禁推理过程）",
      "severity": "严重/中等/轻微",
      "confidence": 0.0
    }
  ]
}
```

几个工程化细节，都是踩过坑后加的硬约束：

- **`think` 与 `reason` 里禁止英文双引号 `"`**：否则会把 JSON 解析搞崩；要引用就用单引号或中文引号。
- **`anchor_text` 与 `original_text` 分离**：`original_text` 求精确（用于展示/对照），`anchor_text` 求可检索（连续、含上下文、不含 `<imgN/>` 占位符），用于在原始 Word 里**唯一精准定位**这条错误。
- **面向用户字段的「用语禁令」**：`description / suggestion / position / correction` 里禁止出现 `detection_content`、`reference`、`has_error` 等内部变量名，也禁止出现 `<imgN/>`、「图片占位符」之类系统标记——因为占位符是系统生成的，不是作者写的内容，建议用户「删占位符」是错的。
- **`suggestion` 禁止犹豫词**：禁止「等等」「让我再看」「难道」这类推理痕迹，必须是干净的操作指令 + 正确文本。

## 路由 Prompt

路由是一个**元 Prompt**：不检测内容，只判定「这题要跑哪些检测」，输出布尔开关字典，缺键即 false。结构、示例和「为什么 fail-closed」见 [05](05-路由与Agent还是工作流.md)。要点重申：**输出示例必须列全所有 task_id**，否则会静默漏检。

## 聚合 Prompt

聚合层 Prompt 把一道题剩余的多条错误连同题干交给 LLM，让它逐条决定 `keep / merge / delete`，可改写描述、但**不得改 error_type**。它被故意写成「以合并为主」，把重型去重让给确定性优先级层。结构见 [08](08-去重与聚合管线.md)。

## 多语言：同结构、分文件

中/日/德/法的检测 Prompt 是**同一套结构、各写一份文件**（如错别字有 `typo` / `ja_spelling` / `de_spelling` / `fren_spelling` 四份）。好处：

- 每种语言可以写本语言专属的错误模式（日文假名/汉字、德文大小写/复合词、法文连字/性数一致），单独调优；
- 结构一致 → 下游解析/聚合/入库完全复用，新增一种语言只是「加一组文件 + 注册任务」。

## 动态 Few-shot：把人工经验注入 Prompt

人工复核时可以把某条判断沉淀为**正例/负例**进案例库。检测时按 `language + task_id + subject + question_type + detection_content + reference` 构造 query，用 sentence-transformers 算向量相似度召回最相似的正/负例，由 `prompt_injector` 注入到检测 Prompt 里，给 LLM 一个「我们以前怎么判类似题」的参考。

工程要点：

- **强过滤**：语言 + task_id 必须匹配（不跨语言召回）；候选再按 subject + question_type 分层回退。
- **相似度门槛**：低于阈值（默认 0.70）不注入，避免「不相关的例子」反而误导。
- **可观测**：检测明细 Excel 会记录是否注入、召回案例 id、相似度、耗时——用来回答「Few-shot 到底有没有生效、有没有帮助」（可在评测主线对照前后指标，见 [10](10-量化指标与评测.md)）。
- **超时治理**：本地 embedding 在高并发审校时单次 query 可能超过 2s，检索超时阈值要给够（否则会误判超时、丢 Few-shot）。

## 一条贯穿始终的 Prompt 哲学

**把 LLM 的输出空间约束到最小**：检测锁死 error_type、路由只输出布尔、聚合只准三个动作、所有输出走同一份 JSON 模板。约束越紧，解析越稳、回归越可测、误报越可控——这是把「不可控的生成」工程化成「可靠的流水线节点」的关键。
