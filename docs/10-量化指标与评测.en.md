"How do you know the effect improved after changing a prompt / swapping the model / adding a case library?" — via the evaluation line, not by gut feel.

## The evaluation line (excel_evaluation)

Upload a **ground-truth-labeled** dataset (`.xlsx/.csv/.tsv`, or packed as zip + an image directory); the system runs it as an `excel_evaluation` task:

```
parse    read questions + labeled error types (incl. global placeholder renumbering, local image bridging)
review   run only the detection tasks matching the labeled error_type (same detection capability)
evaluate compare "labels vs predictions", compute confusion matrix → metrics → evaluation report
```

Using the same detection capability (rather than writing a separate eval path) guarantees "what you evaluate is what runs in production".

## Metric definitions

`EvaluationService` compares labels vs predictions per question and tallies a confusion matrix:

| | Labeled error | Labeled clean |
|---|---|---|
| **Predicted error** | TP | FP |
| **Predicted clean** | FN | TN |

From which:

| Metric | Formula | Meaning |
|---|---|---|
| precision | TP / (TP + FP) | Of what's reported, how much is real (suppress false positives) |
| recall | TP / (TP + FN) | Of real errors, how many were caught (suppress false negatives) |
| F1 | 2PR / (P + R) | Harmonic mean of precision/recall |
| **F2** | 5PR / (4P + R) | **Recall-weighted** F — review prefers over-reporting to missing, so recall matters more |
| FPR | FP / (FP + TN) | False-positive rate |
| accuracy | (TP + TN) / total | Overall correctness |

> **Why emphasize F2**: review is a "better to make people look at a few false errors than to miss a real one" scenario; the cost of a false negative far exceeds a false positive. So F2 (β=2, higher recall weight) fits the business goal better than F1. This is an interview point that shows "metric selection with business consideration".

Failed items are also classified separately (not counted as TP/FP): `skipped_timeout`, `skipped_parse_failed`, `skipped_failed_detection` — avoiding contaminating the effect metrics with "didn't run".

## What this evaluation answers

- **Prompt iteration**: image detection from a weak prompt → forced 4-step reconciliation prompt + Step 4 re-review, and the recall change (weak-impl baseline recall≈0.26 → after the redesign, see the mmdataset-v3 benchmark below: 0.84–0.88 for 27b/plus; details in [07](07-图片审校深挖.en.md)).
- **Case-library effect**: run the same dataset with dynamic few-shot on/off, compare metrics, verify "did the distilled human experience actually help".
- **Model selection**: P/R/F1/F2 of different primary/corrector models on the same eval set.
- **Version regression**: run the eval set after each big change to prevent "fixed A, regressed B".

## mmdataset-v3 benchmark (image-text consistency)

mmdataset-v3 is an image-text consistency eval set of figure-bearing questions (~960+ samples, mostly the positive "image-text inconsistent" class), used to compare models under the same four-stage detection pipeline.

| Model | Form | System | Precision | Recall | F1 | F2 | FPR | Time | TP/TN/FN/FP |
|---|---|---|---:|---:|---:|---:|---:|---:|---|
| **qwen3.6-plus** | hosted · multimodal | new | 0.960 | **0.878** | **0.917** | **0.893** | 0.100 | 35min | 620/234/86/26 |
| qwen3.6-27b | 27B · open weights · self-hostable | new | 0.954 | 0.836 | 0.891 | 0.857 | 0.100 | **28min** | 575/251/113/28 |
| qwen3.6-27b | 27B · open weights · self-hostable | old | 0.957 | 0.860 | 0.906 | 0.878 | 0.099 | — | 601/245/98/27 |

> Only **vision-capable multimodal models** are included; a text-only model can't truly "see" the figure and is unsuitable for the image-text task, so it's excluded from the comparison.

**How to read this table:**

- **plus is best overall**: recall 0.878, F1 0.917, F2 0.893, precision 0.96, FPR only 0.10 — both recall and precision.
- **27b has the best value**: precision on par with plus (0.954), recall 0.836, and **fastest (28min)**; the 27B open weights can be self-hosted on local vLLM — ideal for private / cost-sensitive deployments.
- **The rewrite didn't cost quality**: for the same 27b, old vs new system are nearly identical (recall 0.860 vs 0.836, F1 0.906 vs 0.891), showing the migration from old to new system upgraded the architecture while preserving detection ability.
- **The dataset is model-sensitive**: same data and pipeline, swapping the model shifts results notably — choosing a "vision-capable and well-suited" model is key; with **F2 (recall-weighted)** as the primary review metric, plus reaches 0.893.
- **Positive ratio**: of the ~960+ samples, the positive class (image-text inconsistent) is ~70% (e.g. plus: positives ≈ TP+FN = 706), so false negatives are costly and F2 fits the goal better than F1.

> Note: the weak implementation (no Step 4 re-review, weak prompt) reached only ~0.26 recall on similar data (an early internal snapshot); the table above is the four-stage strong pipeline on mmdataset-v3. The two are different dataset snapshots and not a strictly controlled comparison, but they show the order-of-magnitude lift from the redesign.

## Token accounting

Besides effect metrics, **cost** is also measured:

- The `task_metrics` table records `prompt_tokens / completion_tokens / total_tokens`, split by stage (skeleton extraction / concurrent fill / detection / aggregation, etc.).
- With the batch-stats panel, you can see "which step burns the most tokens" and "long vs short call budgets".
- The project also splits the LLM call budget into long/short tiers (`short_max_tokens` for per-question detection/aggregation, `long_max_tokens` for skeleton extraction/section fill), giving different caps per scenario so short tasks aren't slowed by a long budget and long tasks aren't truncated by a short one.

Putting both "effect" and "cost" quantitative dimensions on the table is what lets you answer the engineering question "is this approach worth it in production".
