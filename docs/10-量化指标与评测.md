# 10 · 量化指标与评测

> [返回首页](../README.md) ｜ 🌐 [English](10-量化指标与评测.en.md) ｜ 上一篇：[09 重试与韧性](09-重试与韧性.md)

「你怎么知道改了 Prompt / 换了模型 / 加了案例库之后效果变好了？」——靠评测主线，而不是凭感觉。

## 评测主线（excel_evaluation）

上传一个带**标注（ground truth）** 的数据集（`.xlsx/.csv/.tsv`，或打包成 zip + 图片目录），系统当成 `excel_evaluation` 任务跑：

```
parse    读题目 + 标注错误类型（含图片占位符全局重编号、本地图片桥接）
review   按标注的 error_type 只跑对应检测任务（用同一套检测能力）
evaluate 对比「标注 vs 预测」，算混淆矩阵 → 指标 → 评估报告
```

用同一套检测能力（而不是另写一套评测逻辑）保证「评测的就是线上跑的」。

## 指标口径

`EvaluationService` 按题对比标注与预测，统计混淆矩阵：

| | 标注有错 | 标注无错 |
|---|---|---|
| **预测有错** | TP | FP |
| **预测无错** | FN | TN |

由此算出：

| 指标 | 公式 | 含义 |
|---|---|---|
| precision | TP / (TP + FP) | 报出来的错里有多少是真的（压误报） |
| recall | TP / (TP + FN) | 真的错里抓回了多少（压漏报） |
| F1 | 2PR / (P + R) | 精确率/召回率的调和平均 |
| **F2** | 5PR / (4P + R) | **召回加权**的 F——审校场景宁可多报也别漏，所以更看重 recall |
| FPR | FP / (FP + TN) | 误报率 |
| accuracy | (TP + TN) / total | 整体正确率 |

> **为什么强调 F2**：审校是「宁可让人多看几条假错，也不能放过真错」的场景，漏报代价远高于误报。所以用 F2（β=2，召回权重更高）比 F1 更贴合业务目标。这是个能体现「指标选型有业务考量」的面试点。

失败项也分类计入（不计成 TP/FP）：`skipped_timeout`（超时）、`skipped_parse_failed`（无法解析）、`skipped_failed_detection`（标记为不可评估），避免把「没跑成」混进效果指标里污染结论。

## 这套评测用来回答什么

- **Prompt 迭代**：图文检测从弱 Prompt → 强制 4 步对账 Prompt + Step4 复审，recall 的变化（弱实现基线 recall≈0.26 → 重构后见下方 mmdataset-v3 基准，27b/plus 达 0.84–0.88；详见 [07](07-图片审校深挖.md)）。同集（mmdataset_final）下「极简 prompt / 单一强 prompt / 四段式全流程 × plus / 27b」的 6 格消融见 [12 消融实验](12-消融实验-prompt与流程.md)。
- **案例库效果**：开/关动态 Few-shot 跑同一数据集，对比指标，验证「沉淀的人工经验是否真的帮上忙」。
- **模型选型**：不同主模型/纠错模型在同一评测集上的 P/R/F1/F2。
- **版本回归**：每次大改后跑评测集，防止「修了 A 退化了 B」。

## mmdataset-v3 基准结果（图文一致性检测）

mmdataset-v3 是含图试题的图文一致性评测集（约 960+ 样本，正类「图文不一致」占多数），用于在同一套四段式检测链路下横向对比不同模型。

| 模型 | 形态 | 系统 | 精准率 | 召回率 | F1 | F2 | FPR | 耗时 | TP/TN/FN/FP |
|---|---|---|---:|---:|---:|---:|---:|---:|---|
| **qwen3.6-plus** | 云端托管·多模态 | 新系统 | 0.960 | **0.878** | **0.917** | **0.893** | 0.100 | 35min | 620/234/86/26 |
| qwen3.6-27b | 27B·开源权重·可本地部署 | 新系统 | 0.954 | 0.836 | 0.891 | 0.857 | 0.100 | **28min** | 575/251/113/28 |
| qwen3.6-27b | 27B·开源权重·可本地部署 | 旧系统 | 0.957 | 0.860 | 0.906 | 0.878 | 0.099 | — | 601/245/98/27 |

> 评测仅纳入**具备视觉能力的多模态模型**；纯文本模型无法真正「看图」，不适用于图文一致性任务，故不参与对比。

**怎么读这张表：**

- **plus 综合最佳**：召回 0.878、F1 0.917、F2 0.893，精准 0.96，FPR 仅 0.10——召回与精准兼得。
- **27b 性价比最高**：精准与 plus 几乎持平（0.954），召回 0.836，且**最快（28min）**；27B 开源权重可本地 vLLM 自托管，适合私有化 / 成本敏感场景。
- **架构重构未损质量**：同为 27b，旧系统 vs 新系统几乎持平（召回 0.860 vs 0.836，F1 0.906 vs 0.891），说明从旧系统迁到新系统在保留检测能力的同时完成了架构升级。
- **数据集对模型敏感**：同一套数据与链路，换模型即影响显著——选对「具备视觉能力且适配」的模型是关键；审校以 **F2（召回加权）** 为首要指标，plus 达 0.893。
- **正类占比**：约 960+ 样本中正类（图文不一致）约占 70%（如 plus：正类 ≈ TP+FN = 706），因此漏报代价高、F2 比 F1 更贴合目标。

> 说明：弱实现版本（无 Step4 复审、弱 Prompt）在同类数据上召回率仅约 0.26（早期内部快照）；上表为四段式强链路在 mmdataset-v3 上的结果，两者数据集快照不同，不构成严格受控对比，但足以说明重构带来的量级提升。

## Token 用量计量

除了效果指标，还计量**成本**：

- `task_metrics` 表记录 `prompt_tokens / completion_tokens / total_tokens`，并按阶段（骨干提取 / 并发填充 / 检测 / 聚合等）拆分 token 用量。
- 配合批处理统计面板，可以看清「哪一步最烧 token」「长调用 vs 短调用预算」。
- 项目里还把 LLM 调用预算拆成长/短两档（`short_max_tokens` 用于单题检测/聚合，`long_max_tokens` 用于骨干抽取/大题填充），按场景给不同上限，避免短任务被长预算拖慢、长任务被短预算截断。

把「效果」和「成本」两个量化维度都摆上桌，才能回答「这套方案在生产上值不值」这种工程问题。
