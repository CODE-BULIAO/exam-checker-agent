### Japanese (4)

`ja_spelling_check` (typo, default on) · `ja_grammar_check` (unclear semantics) · `ja_logic_check` (logic error) · `ja_punctuation_check` (punctuation)

### German (3)

`de_spelling_check` (typo, default on) · `de_grammer_check` (unclear semantics) · `de_punctuation_check` (punctuation)

### French (3)

`fren_spelling_check` (typo, default on) · `fren_grammar_check` (unclear semantics) · `fren_punctuation_check` (punctuation)

> 🐛 **A real historical wart**: the German grammar task id is `de_grammer_check` (misspelled "grammer"). It's referenced in many places across the project, so it **cannot be "fixed" in isolation** — it would ripple through config, mappings and prompt-file paths. In an interview this is a nice example of "how to treat a historical typo": the right move is to comment it, keep references consistent, or schedule a dedicated global-rename migration — not to casually patch one spot.

## Unified error types: decoupling "display taxonomy" from "execution tasks"

What the user sees on the UI is the **unified error type** (10 of them), not the 20 tasks. One unified type maps to language-specific tasks:

```
Unified       zh                ja                  de                fr
Typo          typo_check        ja_spelling_check   de_spelling_check  fren_spelling_check
Unclear       ambiguity_check   ja_grammar_check    de_grammer_check   fren_grammar_check
Option err    options_check     —                   —                 —
Punctuation   punctuation_check ja_punctuation_check de_punctuation_check fren_punctuation_check
Type mismatch mismatch_check    —
Missing info  missing_check     —
Unsolvable    unsolvability_check —
Answer leak   answer_leak_check —
Image-text    image_consistency_check —
Logic error   —                 ja_logic_check
```

**So**: ticking one "Typo" on the settings page makes the backend consider `typo_check / ja_spelling_check / de_spelling_check / fren_spelling_check` together; at execution time the inapplicable ones are filtered out by the paper's language. The results page also aggregates tabs by unified type rather than piling up 20 language tabs.

The value of this layer: a **stable display taxonomy** (users only know 10 categories) while **execution granularity stays flexible** (each language can have a dedicated prompt, tuned and extended separately). The two are decoupled.

## Severity & confidence

Every detected error carries two measures:

- **severity**: `severe / medium / minor`, given by the detection LLM in its output; a separate `error_severity_config` provides a default severity per error type.
- **confidence**: `0.0–1.0`. Most detection prompts set a **reporting threshold of ≥ 0.7** — below it, the error doesn't enter the `errors` list, to suppress false positives.

Both measures are also used during dedup & aggregation: ranking and same-location suppression both consider severity and confidence (see [08](08-去重与聚合管线.en.md)).

## How classification happens

It's worth distinguishing two layers of "classification":

1. **Which detections to run for this question** (routing): decided by the LLM at the routing stage, output as boolean switches. See [05](05-路由与Agent还是工作流.en.md).
2. **Each detection produces only its own error class**: each detection prompt is hard-constrained so the `error_type` field can only be that task's class (e.g. the typo task can only output "typo", never spill over into other types). This makes "error type" **deterministic and task-decided** at execution, rather than letting a single LLM freely label errors — reducing type drift.
