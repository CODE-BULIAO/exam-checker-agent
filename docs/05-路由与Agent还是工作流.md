# 05 · 路由与「Agent 还是工作流」

> [返回首页](../README.md) ｜ 🌐 [English](05-路由与Agent还是工作流.en.md) ｜ 上一篇：[04 错误类别与分类](04-错误类别与分类.md)

这一篇专门回答一个会被面试官追问的问题：**「你这个叫 agent，但看起来更像工作流，到底哪里有 LLM 自主决策？」** —— 诚实地回答。

## 先给结论

它是一条**确定性多阶段流水线**，里面嵌了**两个受约束的 LLM 决策点**：

1. **路由**：每道题判定「跑哪些检测」。
2. **错误聚合**：对一道题的多条报错决定 `keep / merge / delete`。

LLM **不驱动控制流分支、不自我重规划、不动态决定下一步做什么**。所以严格说，它更接近「LLM-in-the-loop 的工作流」，而不是「自主 agent」。下面把两个决策点讲清楚，再讲它为什么仍被叫 agent、以及怎么演进成更 agentic 的形态。

## 决策点一：按题路由

### 它做什么

给定一道题的结构化信息，LLM 输出一组布尔开关，决定下游跑哪些检测；同时给出跳过原因。

**输入（改写示例）：**

```json
{
  "language": "zh",
  "question_type": "单选",
  "question_text": "（题干前 200 字，可能截断）",
  "has_options": true,
  "subject": "物理",
  "section_title": "二、选择题",
  "reference": "（参考材料前 200 字）"
}
```

**输出（改写示例）：**

```json
{
  "typo_check": true,
  "ambiguity_check": true,
  "options_check": true,
  "punctuation_check": true,
  "mismatch_check": true,
  "missing_check": false,
  "unsolvability_check": true,
  "answer_leak_check": true,
  "image_consistency_check": false,
  "skip_reasons": {
    "missing_check": "题干无图/表/材料引用，且无填空标记",
    "image_consistency_check": "题干未出现『如图/见图/下图』等引用"
  }
}
```

### 三条关键设计

- **缺键即 false**：路由 Prompt 明确——输出里缺失的键一律按 `false` 处理，对应检测被跳过。**这是个有意的「fail-closed」选择**，但也意味着：改路由 Prompt 时务必保证输出示例里包含全部 task_id，否则会静默漏掉检测。
- **宁可多检测，不可漏检**：判定细则是「默认 true，仅在『明确不适用』时才置 false」。不确定时输出 true。路由是用来省掉**明显**无效的调用，不是用来激进裁剪。
- **特殊跳过规则优先**：比如「上游解析未完成、题干只剩题号/编号路径」→ 全部检测置 false；「名词解释类极短术语题」→ 跳过歧义/题型/缺失/无解/答案泄露，保留错别字。

### 收益

路由直接减少了对不适用题目的无效 LLM 调用（例如非选择题不跑选项检测、无图题不跑图文检测）。在多任务 × 多题目的批处理里，这类裁剪能省下可观的调用量。

## 决策点二：错误聚合

一道题被多个任务检测后会有多条、可能重叠的报错。在确定性优先级聚合之后，如果还剩多条，会调一个 LLM 聚合层，让它对每条错误决定动作：

- `keep`：原样保留
- `merge`：与其它错误合并，写一条统一描述
- `delete`：删除

**硬约束**：不得修改 `error_type`，动作只能是这三种；且**失败回退不丢错**（LLM 出错或返回无法匹配的 id 时，保留原始错误）。这个层被**故意弱化为「以合并为主」**，重型去重交给确定性优先级层。详见 [08](08-去重与聚合管线.md)。

## 为什么这两处用 LLM、其余用确定性

| 环节 | 实现 | 为什么 |
|---|---|---|
| 步骤顺序（parse→review→查重） | 固定 | 顺序天然确定，无需推理 |
| 解析展平、编号定位 | 确定性 | 要精度，不能让 LLM 自由发挥 |
| 路由（跑哪些检测） | LLM | 「这题该查什么」依赖语义理解 |
| 单个检测产出 | LLM（受约束） | 检测本身是语义任务；但 error_type 被锁死 |
| 同位置同根因去重 | 确定性优先级表 | 规则清晰、要可复现可审计 |
| 语义合并 | LLM（受约束） | 跨表述的合并需要语义判断，但只许 merge/keep/delete |

**原则**：能用规则可复现的地方就用规则（可审计、可回归测试）；只有「需要语义理解、规则写不全」的地方才交给 LLM，而且尽量**把 LLM 的输出空间约束到最小**（布尔开关 / 三个动作 / 锁死 error_type）。这正是它「稳」的原因，也是它「不那么 agentic」的原因——这是个权衡，不是缺陷。

## 那为什么还叫 agent

- 它在「逐题」这个粒度上确实让 LLM 做**自主判断**（这题查什么、这些报错怎么合），而不是把所有题走同一套死规则。
- 它有**多个 LLM 角色协作**：解析的骨干提取、路由、各类检测、图文复审、聚合——像一个分工的「审校小组」。
- 它有**人在回路 + 记忆沉淀**：人工复核结果可沉淀进案例库（动态 Few-shot），回流影响后续检测的 Prompt。

但要对面试官诚实：**当前它不具备「自主规划 / 动态重路由 / 目标驱动的多轮自我修正」**。把它定位成「带 LLM 决策点的可靠工作流」比硬吹「全自主 agent」更可信，也更能体现工程判断力。

## 怎么演进成更 agentic 的形态

- **路由后自反馈**：检测发现大量某类问题时，动态加挂相关检测、或对可疑题二次深检（目前是一次性固定）。
- **聚合升级为带工具的裁决**：让聚合层可调「再查一次某任务」而不仅是 merge/delete。
- **解析失败的自主补救**：解析置信度低时，LLM 自主选择「换策略重抽 / 标记待人工」而非固定回退串行。
- **预算感知调度**：按 token 预算（见 [10](10-量化指标与评测.md)）自主决定检测深度。
