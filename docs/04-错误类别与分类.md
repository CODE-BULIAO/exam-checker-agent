# 04 · 错误类别与分类

## 检测任务全集（20 个）

检测能力以「检测任务」为单位声明（每个任务 = 一个 `task_id` + 一个错误类型 + 一个 Prompt 文件 + 语言分组 + 默认启用标志）。当前共 **20 个任务，覆盖 4 种语言**：

### 中文（10）

| task_id | 错误类型 | 默认启用 | UI 可见 | 说明 |
|---|---|:--:|:--:|---|
| `typo_check` | 错别字 | ✅ | ✅ | 中文错别字/拼写 |
| `ambiguity_check` | 语义不清 | | ✅ | 语病、歧义、句意不清 |
| `options_check` | 选项错误 | | ✅ | 选择题选项结构 |
| `punctuation_check` | 标点符号 | | ✅ | 标点规范 |
| `mismatch_check` | 题型不一致 | | ✅ | 题型与结构一致性 |
| `missing_check` | 信息缺失 | | ✅ | 图表/材料/填空标记缺失 |
| `unsolvability_check` | 题目无解 | | ✅ | 无解或多解 |
| `answer_leak_check` | 答案泄露 | | ✅ | 题干泄露答案 |
| `image_consistency_check` | 图文不一致 | | ✅ | 图文一致性与关键标注完整性（见 [07](07-图片审校深挖.md)） |
| `guide_stem_check` | 题干检测 | ✅ | ❌ | 引导题的大题标题/公共材料/共用选项/阅读材料 |

### 日文（4）

`ja_spelling_check`（错别字，默认开）· `ja_grammar_check`（语义不清）· `ja_logic_check`（逻辑错误）· `ja_punctuation_check`（标点）

### 德文（3）

`de_spelling_check`（错别字，默认开）· `de_grammer_check`（语义不清）· `de_punctuation_check`（标点）

### 法文（3）

`fren_spelling_check`（错别字，默认开）· `fren_grammar_check`（语义不清）· `fren_punctuation_check`（标点）

> 🐛 **一个真实的历史包袱**：德语语法任务的 id 是 `de_grammer_check`（拼成了 `grammer`）。这个 id 被全项目多处引用，**不能孤立地「修正」它**——会牵动配置、映射、Prompt 文件路径。面试时这是个很好的「如何对待历史拼写错误」的例子：正确做法是写注释、保持引用一致，或专门安排一次全局重命名迁移，而不是顺手改一处。

## 统一错误类型：解耦「展示口径」与「执行任务」

UI 上用户看到的是**统一错误类型**（10 个），而不是 20 个 task。一个统一类型映射到多语言的具体任务：

```
统一名      zh                ja                  de                fr
错别字      typo_check        ja_spelling_check   de_spelling_check  fren_spelling_check
语义不清    ambiguity_check   ja_grammar_check    de_grammer_check   fren_grammar_check
选项错误    options_check     —                   —                 —
标点符号    punctuation_check ja_punctuation_check de_punctuation_check fren_punctuation_check
题型不一致  mismatch_check    —
信息缺失    missing_check     —
题目无解    unsolvability_check —
答案泄露    answer_leak_check —
图文不一致  image_consistency_check —
逻辑错误    —                 ja_logic_check
```

**所以**：用户在设置页勾一个「错别字」，后端会同时把 `typo_check / ja_spelling_check / de_spelling_check / fren_spelling_check` 纳入候选；执行时再按试卷语言过滤掉不适用的。结果页也按统一类型聚合 Tab，而不是按语言堆 20 个 Tab。

这层映射的价值：**展示口径稳定**（用户只认 10 个类别），而**执行粒度灵活**（可以为每种语言写专门的 Prompt，单独调优、单独加任务），两者解耦。

## 严重度与置信度

每条检测出的错误都带两个度量：

- **severity（严重度）**：`严重 / 中等 / 轻微`，由检测 LLM 在输出里给出；另有一份 `error_severity_config` 提供按错误类型的默认严重度。
- **confidence（置信度）**：`0.0–1.0`。多数检测 Prompt 设了**报告门槛 ≥ 0.7**——置信度不够不进 errors 列表，用来压低误报。

这两个度量在去重聚合阶段也会被用到：排序、同位置抑制都参考严重度与置信度（见 [08](08-去重与聚合管线.md)）。

## 分类是怎么发生的

值得区分两层「分类」：

1. **该题要跑哪些检测**（路由）：由 LLM 在路由阶段判定，输出布尔开关。见 [05](05-路由与Agent还是工作流.md)。
2. **每个检测只产出自己那一类错误**：每个检测 Prompt 被强约束「`error_type` 字段只能是本任务对应的那一类」（如 typo 任务只能输出「错别字」，不得越界输出其他类型）。这让「错误类型」在执行层是**确定的、由任务决定的**，而不是让单个 LLM 自由地给错误打标签——降低了类型漂移。
